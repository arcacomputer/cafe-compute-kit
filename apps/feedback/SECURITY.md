# App security boundary and known limits

This is a roster-backed private feedback tool, not an unrestricted signup platform or official sponsor service. Access eligibility and benefit eligibility are separate. A configured owner still needs an authorized roster/bootstrap identity and a normal single-use login; an allowlist never fabricates check-in or permits claiming a benefit.

- Only configured canonical HTTPS host requests are routed. POST origin and same-origin fetch metadata, a secure HttpOnly `__Host-` session cookie, session-derived CSRF and POST-only one-use token consumption protect mutations. Magic tokens are random, hashed in SQL and carried only in email URL fragments; GET is not consumption. Sign-in responses do not disclose membership. Per-IP/email/day and global delivery quotas are independent of business feedback quotas.
- Text/identity validation, owned receipt admission and both PostgreSQL business quotas commit atomically. Failed admissions roll back the row and charges. Identical owned retries return the original receipt without a charge; foreign receipts and changed-payload reuse are refused. Cleanup tombstones retain ownership and cannot be overwritten by retries. Ten new receipts per recipient/day and 300 globally/day are deliberate defaults in the SQL function, not a count of attendees or a cohort gate.
- Benefit stock/release state is inaccessible to the public runtime except the constrained allocation function. One assignment per recipient; reviewed positive counts, remaining stock coverage and version must match for real stock. No operation claims provider redemption. Runtime/admin/sender logins must not inherit the operator role.
- Mail credentials exist only on the private sender. It accepts one fixed template, configured origin, exact language/path and database-authorized destination/token. Native SQL atomically reserves one durable attempt. A timeout or provider failure after that reservation is ambiguous and cannot be automatically resent for that token. The main Worker preserves its short-lived issued token during ambiguity so a potentially delivered link can still be consumed once; only an explicitly definitely-not-sent response revokes it. A new authorized login request can issue a new token. This is not exactly-once provider delivery. Keep sender `workers_dev`, preview URLs and public routes off.
- Photos default off. Enabling requires both `PHOTOS_ENABLED=true` and `PRIVATE_PHOTO_METADATA_ACK=true`, plus a private R2 binding. The server checks signatures/MIME, account ownership/CSRF, 20 immutable per-receipt slots and a 4 MiB streamed per-request maximum. This is **not** full image decoding, content moderation, antivirus or EXIF removal. The browser attempts decoding/resizing/re-encoding, which a custom client can bypass. Authorized owners may receive metadata-bearing originals. Do not enable until organizers understand/private-retain that risk; never publish an object-store domain. Photo publication permission remains independent/optional and never gates feedback or benefits.
- Owner photo/export routes are authenticated and no-store. Returned manifests are current, owned and path-checked. Raw prose can identify people; private export is not anonymization. Review all sharing manually.
- Content cleanup is explicit dry-run/manual policy, not an automatic cron. Pause uploads, review exact object keys, delete them manually, acknowledge deletion, then apply only a matching manifest. Tombstones and assignments survive; recipient identities/assignment records remain until a separate reviewed event-retirement decision. Lost provider responses, bucket orphans from failures and database backups require operator attention.
- One event per fresh isolated database/project. SQL capability-role names are cluster-wide. Never replay the old production cohort/pilot migrations (they are not included), reuse another event's roles, copy production inventories or run proof against a real database.

Provider-side restrictions and deployed service/bucket privacy need their own live, authorized checks. Synthetic browser/PostgreSQL proof is not a deployment or email-delivery claim. Report vulnerabilities privately using the repository's root security policy; do not include attendee text, cookies, mail tokens, private codes or photos in public issues.
